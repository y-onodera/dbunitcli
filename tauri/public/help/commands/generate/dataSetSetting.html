dataSetSetting

Generate の unit=table で、テンプレートに渡す前に、1 つのテーブルから条件別の「サブテーブル」を作り、列の値も整形しておくための設定ファイルです。generateType=txt などテンプレート指定タイプで使います（xlsx / xls と固定成果物タイプでは指定できません。固定成果物タイプには組み込み設定が使われます）。

概要

項目説明デフォルト
dataSetSettingサブテーブル設定ファイルのパス（空、組み込み設定を使用）
dataSetSettingEncodingdataSetSetting ファイルの文字コードシステムデフォルト

未指定のときは、generateType に応じた組み込み設定が使われます（ddl / xlsxSchema / javaBean のみ。txt では何も適用されません）。

何のための設定か

unit=table のテンプレートが受け取る rows は「そのテーブルの全行」の 1 つだけです。StringTemplate には行を条件で絞って繰り返す書き方がないため、テンプレートの中で「条件を変えて複数回ループする」ことはできません（例: 状態が OPEN の行と CLOSED の行を別々のブロックに出力する、主キーの行だけを PRIMARY KEY (...) に並べる）。

dataSetSetting は、この絞り込みをテンプレートの外で先に済ませるための設定です。条件ごとにサブテーブルを作っておくと、テンプレートは subTable.{サブテーブル名}.rows を条件の数だけ繰り返すだけで済みます。元のテーブルは rows、サブテーブルは subTable.{サブテーブル名}.rows として参照できます。

ステップやること
(1)dataSetSetting の separate に、条件ごとの要素を並べる（tableName でサブテーブル名、filter で残す行の条件）
(2)テーブルごとのテンプレート呼び出しで、元のテーブルは rows、サブテーブルは subTable.{サブテーブル名}.rows としてテンプレートに渡される
(3)テンプレートで rows や subTable.{サブテーブル名}.rows をそれぞれ繰り返す

サブテーブルを作らなくても、テンプレートが読む前のデータを整えるために使えます。

やりたいことdataSetSetting での書き方テンプレートでの使い方
空欄を「値なし」、"false" を偽として判定したいstring / boolean で式を書き、null や真偽値に変換した列を作る$if(row.列名)$ / $if(!row.列名)$ で判定する
テンプレートに書きたくない判定・変換をまとめたい（型の読み替え、クラス名の組み立てなど）string に式を書いて派生列を足す$row.派生列$ を出力するだけにできる
使う列・行を絞りたい、並べ替えたいinclude / exclude / filter / order / distinctそのまま rows を繰り返す

判定や抽出のロジックを dataSetSetting に寄せると、テンプレート側の式が単純になります。逆に、テンプレートが参照する列・サブテーブルは dataSetSetting が用意しておく必要があります。

基本の例: 条件別に 2 回ループする

入力（ORDERS.csv）

IDNAMESTATUS
1AppleOPEN
2BananaCLOSED
3CherryOPEN

dataSetSetting — 状態ごとのサブテーブルを作ります。

{
  "settings": [
    {
      "name": "ORDERS",
      "separate": [
        {"order": ["ID"]},
        {"tableName": "OPEN_ROWS",   "filter": ["STATUS == 'OPEN'"]},
        {"tableName": "CLOSED_ROWS", "filter": ["STATUS == 'CLOSED'"]}
      ]
    }
  ]
}

テンプレート — 条件ごとのサブテーブルを、それぞれ繰り返します。

== $tableName$ ==
[OPEN]
$subTable.OPEN_ROWS.rows:{row | $row.ID$: $row.NAME$}; separator="\n"$
[CLOSED]
$subTable.CLOSED_ROWS.rows:{row | $row.ID$: $row.NAME$}; separator="\n"$
[ALL]
$rows:{row | $row.ID$: $row.NAME$ ($row.STATUS$)}; separator="\n"$

出力

== ORDERS ==
[OPEN]
1: Apple
3: Cherry
[CLOSED]
2: Banana
[ALL]
1: Apple (OPEN)
2: Banana (CLOSED)
3: Cherry (OPEN)

ポイントは次の 2 つです。

  • サブテーブルは元の全列を引き継ぎ、filter に合った行だけが入ります。条件は何個でも並べられ、filter は複数指定すると AND になります。
  • 元の行（rows）も使うときは、tableName を付けない要素を 1 つ入れます。ここでは order を指定した要素がそれにあたります。すべての要素に tableName を付けると、元のテーブルは rows が空になり、サブテーブルだけが残ります。中身が空の {} も「元のテーブル」として残らないため、order など何か 1 つ指定してください。

設定の pattern が .* のときの重複に注意してください（「仕様」の注意点を参照）。

仕様

dataSetSetting は Dataset Settings と同じ JSON 形式（settings / commonSettings）の設定ファイルです。src の setting を適用した後の状態に対して、テーブルごとにテンプレートへ渡す前に適用され、テンプレートから見えるデータの形を次の 3 点で変えられます。

  • rows: 各行に持たせる列（値・型）、残す行、並び順
  • subTable: どのテーブルがあるか（サブテーブルの追加・名前）と、各テーブルのカラム情報
  • 適用範囲: どのテーブルに適用するか

テンプレートに渡る変数

変数内容dataSetSetting の影響
tableNameテーブル名（例: EMPLOYEE）なし（元のテーブル名のまま）
columns / primaryKeys / columnsExcludeKey入力データのカラム定義なし。設定後のカラム情報は subTable.{テーブル名}.columns などで参照する
rowsこのテーブルの行（row.列名 で参照）あり。追加した列は各行の末尾に付き、同名の列は上書きされる。元の列は残る。include / exclude / filter / order / distinct もここに反映される
subTable設定の結果できたテーブルの一覧（subTable.{テーブル名}.rows）。キーはテーブル名の昇順。unit=table では、そのテーブル単位と、dataSetSetting の separate で作ったサブテーブルだけが入る（src の setting で分けた他のテーブルは、別名を付けたかどうかに関わらず含まれない）あり。separate で作ったサブテーブルが subTable.PK のように加わる。各テーブルの columns / primaryKeys にも設定が反映される

設定キーとテンプレートへの影響

キー書式の例テンプレートへの影響
string / boolean / number"string": {"LABEL": "NAME + '-' + PRICE"}式（JEXL）の結果を新しい列として rows に追加する。式では同じ行の列名を変数として使える。型は string / Boolean / 数値。同名の列は上書きされる

注意点

  • 値の型: 設定がない列の値はすべて文字列です。文字列の "false" や空文字 "" もテンプレートの $if(...)$ では真になります。真偽や「空欄は値なし」で判定したい列は、boolean や ? : で null に変換してください。
  • 存在しない列: 入力に無い列名を式で参照するとエラーになります。
  • サブテーブルへの再適用: pattern が .* のままだと、separate で作ったサブテーブルにも設定が再度適用され、行が重複します。サブテーブル名は exclude で除外してください（組み込みの ddl / xlsxSchema がそうしています）。
  • split と結合: split で分割しても、subTable には最後の断片だけが残ります。innerJoin / outerJoin / fullJoin の結果は subTable に現れません。どちらもテンプレート生成には向きません。

組み込みでの使われ方

ddl / xlsxSchema / javaBean は、次のような dataSetSetting を内蔵しています（Scaffold でワークスペースへ書き出せます）。上の考え方をそのまま使っており、自分でテンプレートを書くときの手本になります。

generateType組み込みの設定ファイル条件別ループとしての使われ方
ddlsql/ddlSettings.json全カラムを rows で繰り返して列定義を出し、filter: ["IS_PK"] で作った PK サブテーブルを subTable.PK.rows で繰り返して PRIMARY KEY (...) を出す（全行ループと主キーのみループの 2 回）。あわせて空欄の null 化と NULLABLE / IS_PK の真偽値化も行う
xlsxSchemaxlsxschema/xlsxSchemaSettings.jsonrows（ヘッダー・列位置）に加え、PK（主キーのみ。breakKey 用）と CELLS（セル位置用。cellAddress 用）の 2 つのサブテーブルを作り、JSON の項目ごとにそれぞれ繰り返す
javaBeanjavabean/javaBeanSettings.jsonサブテーブルは作らず、全テーブルに共通で派生列（className / javaType / isBoolean など）を足して、テンプレートの判定を不要にする
fixedColumnDef（組み込みなし。Scaffold のサンプル fixedcolumndef/fixedColumnDefSettings.json）テンプレートが読む列（name / length / align / pad）をそのまま通すだけのサンプル。他のデータソースの列名に合わせて書き換える起点にする

固定成果物タイプの設定は、generateType=txt に切り替えて dataSetSetting に自作のファイルを指定すると差し替えられます（下の例 1・例 2 参照）。

例 1: ddl の組み込み設定とテンプレートを読み解く

ddl の組み込み設定（sql/ddlSettings.json）とテンプレート（sql/ddlTemplate.stg）で、dataSetSetting の有無によるテンプレートの動きの違いを示します。どちらも Scaffold ダイアログ（generateType=txt のとき unit の上の Scaffold ボタンから開く）でワークスペースに書き出して編集でき、フォームの dataSetSetting / template に指定して使います。

1. 入力（記述子データセット） — 1 カラム = 1 行で、テーブルごとに渡されます（例: EMPLOYEE）。以降の出力例は、この入力を CSV にして実際に生成した結果です。

COLUMN_NAMETYPE_NAMECOLUMN_SIZEDECIMAL_DIGITSNULLABLEIS_PKPK_NAMEREMARKSTABLE_REMARKS
EMPLOYEE_IDINTEGER10（空）falsetruePK_EMPLOYEE社員ID社員マスタ
EMPLOYEE_NAMEVARCHAR100（空）truefalse（空）氏名社員マスタ
SALARYDECIMAL102truefalse（空）給与社員マスタ

2. dataSetSetting（ddlSettings.json の抜粋）

{
  "settings": [
    {
      "pattern": {"regex": ".*", "exclude": ["PK"]},
      "separate": [
        { "string": {
            "COLUMN_NAME": "COLUMN_NAME",
            "TYPE_NAME": "TYPE_NAME",
            "COLUMN_SIZE": "COLUMN_SIZE != null && !COLUMN_SIZE.isEmpty() ? COLUMN_SIZE : null",
            "DECIMAL_DIGITS": "DECIMAL_DIGITS != null && !DECIMAL_DIGITS.isEmpty() ? DECIMAL_DIGITS : null" },
          "boolean": { "NULLABLE": "NULLABLE", "IS_PK": "IS_PK" } },
        { "tableName": "PK",
          "filter": ["IS_PK"],
          "string": {"COLUMN_NAME": "COLUMN_NAME", "PK_NAME": "PK_NAME"} }
      ]
    }
  ]
}

これにより次の 3 つの整形が行われます。

  • 空文字を null に変換（COLUMN_SIZE / DECIMAL_DIGITS）: 空欄のカラムをテンプレートの $if(row.COLUMN_SIZE)$ で「値なし」と判定できるようにします。
  • 真偽値へ変換（NULLABLE / IS_PK）: 文字列 "false" を偽として $if(!row.NULLABLE)$ で判定できるようにします。
  • 主キー行を PK サブテーブルへ分割（separate + filter）: テンプレートから subTable.PK.rows として主キーのカラムだけを参照できます。

3. テンプレート（ddlTemplate.stg の抜粋）

ddlType(row) ::= <<$row.TYPE_NAME$$if(row.COLUMN_SIZE)$($row.COLUMN_SIZE$$if(row.DECIMAL_DIGITS)$,$row.DECIMAL_DIGITS$$endif$)$endif$>>
createTable() ::= <<
CREATE TABLE $tableName; format="upper"$ (
    $rows:{row | $row.COLUMN_NAME; format="upper"$ $ddlType(row)$$if(!row.NULLABLE)$ NOT NULL$endif$}; separator=",\n    "$
    $if(subTable.PK.rows)$,CONSTRAINT PK_$tableName; format="upper"$ PRIMARY KEY ($subTable.PK.rows:{row | $row.COLUMN_NAME; format="upper"$}; separator=", "$)
    $endif$
);
>>

テンプレートに書かれているのは「サイズがあれば (サイズ) を付ける」「NOT NULL ならそう出力する」「subTable.PK があれば主キー句を出す」だけで、型の判定や主キー行の抽出といったロジックは dataSetSetting 側が受け持っています（組み込みテンプレートは PK_NAME があればそれを制約名に使いますが、抜粋では省略しています）。

5. レンダリング結果の比較

dataSetSetting あり（ddlSettings.json）dataSetSetting なし（generateType=txt で未指定）
CREATE TABLE EMPLOYEE (
    EMPLOYEE_ID INTEGER(10) NOT NULL,
        EMPLOYEE_NAME VARCHAR(100),
        SALARY DECIMAL(10,2)
    ,CONSTRAINT PK_EMPLOYEE PRIMARY KEY (EMPLOYEE_ID)

CREATE TABLE EMPLOYEE (
    EMPLOYEE_ID INTEGER(10,),
        EMPLOYEE_NAME VARCHAR(100,),
        SALARY DECIMAL(10,2)
);

dataSetSetting が無いと、テンプレートが前提とする整形が行われないため、次のようにテンプレートを書いても期待どおりに動きません。

  • NOT NULL が付かない（EMPLOYEE_ID に付かない）: NULLABLE が文字列のままだと "false" も真として扱われ、$if(!row.NULLABLE)$ が常に偽になります。
  • 主キー句が出ない: PK サブテーブルが作られないため subTable.PK.rows が空になります。
  • 空欄の判定ができない: DECIMAL_DIGITS の空文字が値ありと扱われ、INTEGER(10,) や VARCHAR(100,) のように不正な型指定が出力されます。

例 2: 組み込みを改造する（コメントの既定値を追加）

組み込みの DDL では、備考（REMARKS）が空のカラムは COMMENT ON COLUMN ... IS '' と空のコメントになります。ここでは、備考が空ならカラム名をコメントにするように、dataSetSetting とテンプレートの両方に手を加えます。

1. dataSetSetting: 判定を設定側に追加する — ddlSettings.json の最初の separate の string に、COMMENT_TEXT を 1 行足します。

"string": {
  "COLUMN_NAME": "COLUMN_NAME",
  "TYPE_NAME": "TYPE_NAME",
  ... （既存の定義）
  "COMMENT_TEXT": "REMARKS != null && !REMARKS.isEmpty() ? REMARKS : COLUMN_NAME"
}

2. テンプレート: 追加した変数を参照する — ddlTemplate.stg の commentOnColumns() を、COMMENT_TEXT を使う形に書き換えます。

commentOnColumns() ::= <<
$rows:{row | COMMENT ON COLUMN $tableName; format="upper"$.$row.COLUMN_NAME; format="upper"$ IS '$row.COMMENT_TEXT$';
}$
>>

3. 結果 — 入力の SALARY の備考が空のとき:

組み込みのまま改造後
COMMENT ON COLUMN EMPLOYEE.EMPLOYEE_ID IS '社員ID';
COMMENT ON COLUMN EMPLOYEE.EMPLOYEE_NAME IS '氏名';
COMMENT ON COLUMN EMPLOYEE.SALARY IS '';
 
COMMENT ON COLUMN EMPLOYEE.EMPLOYEE_ID IS '社員ID';
COMMENT ON COLUMN EMPLOYEE.EMPLOYEE_NAME IS '氏名';
COMMENT ON COLUMN EMPLOYEE.SALARY IS 'SALARY';

テンプレートだけを書き換えて dataSetSetting に COMMENT_TEXT を足さないと、テンプレートが参照する変数が存在しないため、コメントはすべて空（IS ''）になります。テンプレートが参照する変数・サブテーブルは、対応する dataSetSetting とペアで編集してください。書き出した設定とテンプレートは、フォームの dataSetSetting / template に指定すると組み込みの代わりに使われます。

手を加える範囲の目安は次のとおりです。

  • 表示を変えるだけ（文言・並び・インデント）: テンプレートだけを編集する。
  • 判定や変換を足したい（空欄の既定値、型の読み替え、条件分岐の元になるフラグ）: dataSetSetting に string / boolean を足し、テンプレートで参照する。
  • 一部の行を別に扱いたい（主キーだけ、特定の列だけ）: dataSetSetting の separate + filter でサブテーブルを作り、テンプレートで subTable.{名前}.rows を参照する。
